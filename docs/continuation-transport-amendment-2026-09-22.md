# 9/22 传输修复（不改变任务与方法）

第一版 `continuation_pro` 的 120 秒 timeout 发生 `APITimeoutError`。
启动修复时仅检查基础设施类型/耗时和调用完成数，未据测试准确率调模型或方法。
旧目录与冻结源码完整保留。停止旧 runner 时在途请求可能仍在供应商执行，
没有响应的请求 usage/费用未知，不能从 ledger 计费推断它们免费。

第二版 `continuation_pro_v2` 将 timeout 提升至 300 秒，其余模型、prompt、
masks、训练/验证、统计规则全部不变。逐 job_id 复用旧目录**成功返回**的完整
结果（包括答错、格式错和截断结果），不重新请求。已有超时和未返回请求做一次
恢复请求；复用清单及旧失败/在途清单写入 `recovery.json`。仍失败则保留缺失，
不重复直到成功。第一版不是新的独立实验样本，不与第二版重复计数。

Mem0 / LightMem / A-Mem 的开发运行也使用相同修复后的 timeout。若纯依赖或
序列化故障发生在写入之后，保留原始调用，不将接口排查分数当正式系统结果。
A-Mem paper 的相邻 checkout 与冻结 clean 检查不一致时，独立检出指定 commit；
不更改相邻目录。所有适配改动先过开发接口检查再跑冻结测试。

正式 runner 结束后，对第二版中新出现、**尚未恢复过**的基础设施失败允许一次
相同输入恢复；没有失败状态的答错/格式错/截断响应绝不重试。已在第一版恢复
清单中的请求若又失败，则不再试。此规则在正式面板完成前固定；新响应写入
独立 `transport_recovery` overlay，旧 ledger 不变，报告按 job_id 合并，
费用按实际请求累计。若训练曾因缺失而 withheld，补齐后才首次运行其冻结验证臂；
不替换失败案例、不修改 discovery 设置或 prompt。
