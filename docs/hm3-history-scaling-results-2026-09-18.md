### 2.5 审计：graph 的 EES 偏移来自哪里（seed 0 逐 episode 追踪，2026-09-18 晚）

判定之前按"结果不符预期先查实现"的规则做了逐 episode 追踪。方法：对每个 EES 翻转的 episode，
把 (native 训练集 / 该档训练集) × (native episode / 该档 episode) 四格分别评测；再对 gate 的特征向量逐块比较；
再把 parser 的 regime 估计换成"只用真实记录"的对照（用外来记录的 `x*` rid 前缀过滤，只是诊断，不是方法臂）。
四格对照脚本为 `code/hm3/diag_graph_2x2.py`（汇总 `diag_graph_2x2_agg.py`）；逐 episode / 逐特征块的追踪脚本留在 session scratchpad。

**增广本身是干净的。** oracle 与 rh_oracle 在所有档位、所有 seed 上没有任何 episode 翻转；augment 后真实记录、
真实对象逐字段与 native 相同；native 训练集没有被 augment 过程改写。runner 的 native 档与 `det_dev_*.json`
旧面板逐数字一致（Travel graph 0.833，Shopping32 graph 0.750 / program_reg 0.850 / superset 0.000）。

**偏移的唯一特征来源是 regime 估计块。** 同一 (episode, parent, child) 的 gate 特征在 native 与 50 档训练集之间
只有 `est_vector(parent)` 与 `est_vector(child)` 两块不同（Travel seed 0：分别占 11% 与 7% 的训练行），
其余块（数值差、邻域重叠、sibling rank、would-change）逐元素相等。差异的来源有三条通道：

1. **外来 witness 补上真实历史从未见证的 key。** B/C 世界是同一世界的改名副本，policy key（hotel、provider、
   restaurant、vendor；Shopping 的 category 与 promo）不改名；D 世界在 Shopping 里共享 category 级 key。
   真实链未 consult 的 key 在 native 下是 −1（未知），增广后被外来记录定义。Travel seed 0 训练集 50 档：366 个
   (episode, key) 从未知变为有值；Shopping32 seed 0 训练集 100 档：185 个 episode 中 177 个至少一个 key 改变，
   compat 族 521 处、strict_promo 49、auto_promo 42、enforce_budget 36。
2. **外来 witness 覆盖真实 witness（仅限未 consult 的 key）。** §9.1 的交错规则只保护被 consult 的 key：不为
   consult key 产生 witness 的外来 segment 可以插在真实 segment 之间，因此对真实历史见证过但本 episode 不 consult
   的 key，更晚的外来 C witness 成为最后 witness。Travel seed 0 训练集 50 档有 255 处 val→val 的覆盖
   （例：`enforce_late[H11]` 1→0，witnesses x23/x25）。§3 表中"冲突 witness 被后面的真实 witness 覆盖"只对
   consult key 成立，对其它 key 不成立；这是设计页应补的一句。
3. **状态快照推断。** Travel parser 最后一步"可见 late 标志蕴含 enforce_late=1"遍历 S0 里全部 stay；外来 stay
   与真实 stay 同 hotel 名，于是仅凭外来对象的状态就定义了真实 key。这条通道连"只用真实记录"的对照也去不掉，
   是 Travel 里 c100 档偏移最大的原因（`est` 断言失败 `enforce_late[H58]` 3 次亦由此而来）。

**graph 为什么会受影响。** LearnedGraph 的 gate 特征包含所触及对象全部 key 的 regime 估计，would-change 项
用同一估计模拟局部值规则；gate 的 label 带 fields（如 stay 的 `late_arrival`）。估计从"未知"变为"有值"或被
覆盖后，深度 5、叶最小 2 的决策树在训练时学到不同的分裂，在评测时对同一 native episode 给出不同的 fields
（value_accuracy 0.5/0.67 的翻转）或多/少一个动作（affected recall 0.75、collateral 1 的翻转）。值通路本身
（`restricted_est`/tracker 读 consult key）不受影响，因为 §6 断言保证了 consult key 的 est 与 prov。

**第二个混淆：训练集不再配对。** §6 断言失败的训练 episode 被丢弃（Travel 每档 1–3 个；Shopping32 seed 0
100 档 15 个、500 档 34 个）。只去掉一个训练 episode，决策树就在 dev 60 个 episode 上翻转 1–4 个。评测集按
episode 配对，但训练集在档位之间并不配对，这是 P2 判据没有考虑的方差来源。

### 3.1 复核：graph_closed 在 100/500 档比 native 档更高的原因（2026-09-18 晚）

同一批 62 个 episode 上 graph_closed/compact 的 EES 为 native 0.21、100 档 0.39、500 档 0.34，而它的 prompt 本应
只依赖真实对象与记录。检查 ledger：三档 prompt 长度完全相同的只有 28/62 个 episode；其余 episode 在增广档位的
选择更大（例如 test-004：native 9 个对象 / 3 条记录，100 档 19 / 7）。原因是 selector 按设计在同一档位的增广
train 上重新拟合（设计 §4），拟合出的决策模型在增广数据上判定更多对象为 changed，read 集合与 closure 随之变大，
actor 因此拿到更多上下文。returned_model、parse_ok（1.00）、finish_reason（stop）三档相同，排除了模型或截断差异。

结论：graph 臂跨档位的 EES 上升来自 selector 重拟合导致的选择变大，不来自干扰记录本身；这与 round 3/4 的
"closure 越完整 actor 越好"一致。为把长度效应与 selector 重拟合分开，增加 `--selector_history native`：
selector 只在 native train 上拟合，此时 graph 的选择按构造与档位无关、prompt 逐字相同。100/500 档的
`travel_{100,500}_natsel` 正在运行（只跑 graph_closed 两种序列化），其 EES 应与 native 档一致（差异即
actor 的采样噪声）；论文主表将同时给出两种 selector 口径。full / bm25 / recency 臂不受此影响。

### 3.5 复核发现的标注伪影与 v2 重跑（2026-09-18 深夜）

### 3.6 针对 native 差距的 selection 修订：graph_seg

round 3/4 与本轮 natsel 分析都指向同一件事：actor 拿到的 witness 越完整越好。`graph_seg` = graph_closed 的
读取集合 ∪ 每条被选 witness 所在的整个 segment（产生该 witness 的 intervention 记录与其后全部效果记录）∪
这些记录 referent 的 1-hop closure。dev seed 0 的一个 episode：graph_closed 6 条记录 / 14 个对象，graph_seg
11 / 17，prompt 3.4k → 4.0k 字符。在 Travel native（compact + verbose）与 500 档（compact）上运行，
预测：native 档相对 full/verbose 的差距缩小，500 档仍远高于 full。

结果（test seed 30，63–64 episode，配对）：native 档 graph_seg/compact EES 0.30（graph_closed/compact 0.22，
full/verbose 0.55；seg − full −0.25 [−0.39, −0.09]），graph_seg/verbose 0.43（graph_closed/verbose 0.35，
full/verbose 0.54；seg − full −0.11 [−0.27, +0.05]）；500 档 graph_seg/compact 0.32（graph_closed 0.33，full 0.06；
seg − full +0.25 [+0.13, +0.38]），input tokens 3.2k。整段 witness 让 native 差距缩小约 0.08，verbose 序列化下
与 full 的差距落在非劣边界附近；500 档不变。结论：native 档的差距是"历史短到可以全读时，全读最好"的成本，
selection 在此处付出 0.1–0.25 的 EES 换取 60–75% 的输入；历史变长后反转为 +0.25 以上。论文按这个 crossover
写，不再试图在 native 档赢过 full。

### 3.9 单类型分解的中期结果与公平性诊断（2026-09-19 凌晨）

Travel 100 条，graph_closed/compact 对 full/verbose，同一批 episode（n=23–38，仍在运行）：

| 干扰类型 | graph_closed/compact | full/verbose | full 的 input tokens |
|---|---:|---:|---:|
| a100 同对象旧版本（约 26 条） | 0.32 | 0.39 | 10k |
| b100 一致的重复 witness | 0.29 | 0.50 | 41k |
| c100 同 key 的冲突 witness | 0.35 | 0.04 | 54k |
| d100 无关世界 | 0.25 | 0.46 | 42k |

读法：100 条记录的 full 崩溃几乎全部来自 **C 型冲突 witness**；纯体积（D）与一致重复（B）在 40k tokens 下
不伤害 full，旧版本克隆（A）也不伤害。graph 臂在四种类型下都在 0.25–0.35。

由此产生一个必须回答的公平性问题：C 型条件下真实 witness 按构造排在冲突 witness 之后，parser 的
"最后一个 witness 生效"规则让 graph 自动取到正确值；actor 的 system prompt 却写着"同 id 的实体共享同一
policy"，没有告诉它冲突时以更近的记录为准。graph 的优势是否只是这条未告知的规则？诊断（已启动）：

1. `travel_c100_v3`、`travel_500_v3`：prompt v3 = v2 + 明确的冲突规则（"同一实体的记录冲突时，历史中更靠后
   的记录反映当前 policy"），full/verbose 与 graph_closed/compact 都用 v3 重跑。若 full 在规则下恢复，
   graph 在 C 型上的优势就要改写为"结构把时间规则实现在选择里，而 actor 需要被显式告知"；若不恢复，
   优势来自选择本身。
2. `travel_d500`：只加无关世界到 500 条（约 240k tokens），检验纯体积是否让 full 崩溃。
3. 第二个 test seed 31 与 program 选择臂仍在运行。

500 档 abcd 混合里 C 型占外来记录的三分之一；v2 重跑中 full/verbose 在 500 档为 0.17、graph 0.52（中期）。

**诊断结果（2026-09-19 凌晨，n=63–64，配对，test seed 30）：**

| 条件 | graph_closed/compact | full/verbose | graph − full [95% CI] |
|---|---:|---:|---|
| c100（冲突 witness）prompt v2 | 0.32 | 0.08 | +0.24 [+0.11, +0.37] |
| c100 prompt v3（明确"冲突时以更近记录为准"） | — | 0.08 | full v3 − v2：+0.00 [−0.10, +0.10] |
| 500 abcd prompt v2（v2 重跑） | 0.37 | 0.13 | +0.24 [+0.10, +0.38] |

1. 把"冲突时以更近记录为准"写进 prompt 不能救回 full（c100 仍 0.08；500 档反而 0.13 → 0.05）。graph 的
   优势不是一条未告知的规则，而是 actor 在长历史里无法可靠执行这条规则，而结构化选择把它实现在读取阶段。
2. 纯体积不使这个 actor 崩溃：d500 的 full 在约 240k tokens 下为 0.41，与 native 的 0.53 相比只降一些，
   仍高于 graph 的 0.33（差 −0.10，区间跨 0）。所以"full 随长度崩溃"必须改写为"full 随**同实体冲突证据**
   的累积崩溃"；只有体积时，selection 的收益是用 1–3% 的输入换取相当的准确率。
3. seed 31 复现 seed 30：native −0.34，500 档 +0.22。
4. 由此，论文的 Travel actor 层主张应写成两条：(i) 成本——在纯体积的长历史上，学得结构以 1–3% 的输入达到
   与全读相当的成功率；(ii) 稳健性——当长历史包含关于同一实体的冲突或过期证据（policy 漂移、其他上下文的同名
   实体）时，全读与固定 K 检索崩溃到 0.1 以下，学得结构保持 0.3 以上。前提是当前世界自己的 witness 是该
   key 最新的记录（增广按此构造；provenance 设计与 scaling 设计 §3 已写明）。

## 5. 结论槽

当前可以写的结论（2026-09-18 深夜；Shopping 100/500 档 API 与三 seed 确定性面板仍在补齐）：

1. **确定性层（Travel）**：学得图的读取量与 EES 在 native → 500 条记录下持平（P1、P2），固定 K 的检索
   丢失必需记录（P3），读取全部历史的方法读取量线性增长（P4）。selection ladder 上 graph_select 三档全为
   1.000，三个重接线的 wrong_select 为 0.60 / 0.03 / 0.03，bm25_k16 从 0.95 跌到 0.03。
2. **actor 层（Travel，DeepSeek-V4-Flash，test seed 30，63–64 episode）**：native 档 graph_closed/compact
   低于 full/verbose 0.33 [0.19, 0.47]（round 3/4 的方向）；100 与 500 档反转为 +0.33 [+0.20, +0.46] 与
   +0.27 [+0.13, +0.43]，graph 的 input tokens 三档 2.2k–2.8k，full/verbose 8k → 55k → 237k；bm25_k16 与
   recency_k16 在 100/500 档与 full 同样接近 0。selector 固定在 native train 上时结论不变（+0.27 / +0.24）。
   graph 臂自身跨档位上升 0.09–0.16 的机制是长历史里同一实体的额外 witness 被图选中（§3.4），如实报告。
   **分解（§3.9）**：full 的崩溃来自冲突 witness（c100 0.08），不来自体积（d500 在 240k tokens 下 0.41）；
   明确告知冲突规则的 prompt v3 不能救回 full；seed 31 复现。主张改写为"成本 + 对冲突证据的稳健性"两条。
3. **更强 backbone（DeepSeek-V4-Pro）**：native 差距收窄到 −0.10 [−0.28, +0.08]；500 档 +0.07
   [−0.09, +0.22]，full/verbose 0.38 → 0.17。方向一致，幅度更小。
4. **Shopping32（actor 层）**：native 档 graph 与 full 无差别（−0.07 [−0.21, +0.08]），100/500 档 graph 与
   full/recency 相近（+0.00 / +0.06），full 未像 Travel 那样崩溃（0.40 / 0.24）。Shopping 的 cart 两跳内
   全连通，图对选择的增量小，这与 selection ladder 上 wrong_select 无区分力一致。
5. **同图反向 provenance（Travel，test seeds 30–32）**：top-1 命中 0.55–0.65、top-3 0.98–1.00；替换 top-3
   后 EES 恢复 0.98–1.00，matched random-3 为 0，similar / recency 为 0，BM25 定位基线 p@3 ≤ 0.60；500 条
   记录下 p@3 0.94–0.98。正向选择与反向追踪使用同一 graph SHA。Shopping32 未通过（witness 被污染静默，
   provenance 设计 §7.4），作为边界报告。
6. **未完成 / 边界**：Shopping 100/500 档 API 还差 7 与 17 个 episode；三 seed 确定性面板由第二个 session
   补齐；Mem0 / dense 未做（无 embedding 端点，用户决定不做）；A-Mem 依赖已装（`benchmarks/A-mem`，
   sentence-transformers / chromadb / litellm），LightMem 源码已克隆但其包要求 Python < 3.12（本机 3.13.9），
   只能以源码路径方式接入，两者尚未接入 HM3，属于 MemoryArena 层的工作。
