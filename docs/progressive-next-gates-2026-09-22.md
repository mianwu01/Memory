# 负结果之后，恢复研究推进的门槛

继续使用deepseek-v4-flash与thinking。当前冻结开发结果不支持扩大同一
topic图方案；不重跑已关闭实验，不以更多discovery算法名称替代必要证据。
本页是后续工作的条件，不代表这些条件已经满足，也不是Yujia对对象的认可。

## 1. 先修可验证的actor与证据接口

保持固定开发ID 0–9。原输出与原严格评分永不覆盖。下一版若要调用API，
应先另立版本，写明通用接口变化、重试/截断规则与开发迭代预算；不得逐题
提供答案、逐题增加别名或把成功案例替换进开发集。仍要求至少27/30严格
正确、至少9题3/3、无截断或未恢复基础设施失败，随后冻结配置。

可见缺口有两类：case8等含正确实体但格式不合规；case3的作品混淆、
case4/5/7的证据获取或判断不足。修格式不会自动解决实质错误。不得把
case3/5/7已有答案字面当作已满足全部题目条件；应检查关系与实体消歧。

当前SQLite BM25并非作者的稠密检索器。作者公开索引的构建模型与搜索类
默认模型还不一致；现有API的embedding探针返回404。后续若恢复该后端，
必须核对query与文档向量兼容性；不能仅加载索引就声称复现了作者设置。
还需核对服务端报告的输出token超限问题，否则只能称请求预算一致。

## 2. 先落实记忆机制，再拟图

保留实际native write时钟、任务边界、输入输出原文和来源读取。新表示必须
说明变量属于哪项agent实际使用的记忆，如何被更新、何时读取，以及哪些
变化来自query外部驱动。当前四维NMF只是有损文本投影，不能改名为语义
字段、潜在机制或可靠SCM。原始任务分解由数据集给定，不能归于发现。

若需换研究对象，先形成可审查的变量/转移/混杂说明和无答案泄漏的样例；
不得把更换对象称为Yujia已认可。候选必须经静态审查和原生运行检查，不能
先大批调用再把偶然正结果包装为机制。外部沟通另需明确发送授权。

## 3. 在新增大批调用前做输入级反证

完整保存discovered、空图topic_only、complete、真实不同的错误图及简单
检索的输入。若删去全部发现边仍不改变任何读取请求，就停止边贡献主张。
当前方案已触发这条停止条件，换置换seed或增加bootstrap不能修复它。

只有actor、变量有效性与结构消费检查均通过，才冻结训练/测试协议，执行
独立测试及同协议代表性memory systems。Mem0/A-Mem/LightMem旧面板不拼表。
全部写入、拟合、开发失败、读取、替代来源和缓存成本均计入；不能只比较
reader输入长度，也不能把同输入共享响应当作独立试验。

## 4. 同一结构必须支持可验证的安全处置

先冻结正常full稳定正确的案例和权限政策；报告全部案例及不适用项。
定位候选不等于发现问题源。应检验实质信息替换、冗余路径下的阻断、中性
变更、真实授权替代，以及证据不足时的拒答。权限与真伪分开核验。

当前单条删除保持正确、反事实替换未跟随、来源闭包退化为空记忆；授权
重取仅三例稳定正确，证据隔离也没有修复剩余错误。因此不能写成审计闭环
成立。下一版应针对这几个明确失败机制，而非继续挑案例直到出现正例。
