## 推算依据与不确定性

- Actor：按每 round 2 次调用。历史相同 111–113 IDs，四组方法分别用了 44/42/45/44 次，覆盖每组 22 rounds；约 2 次/round 有实测依据。新 baseline 可能改变轮内工具交互次数，预留项覆盖一部分变化。
- Summary：每次 write 1 次，超预算时增加一次压缩，按 1–2 次/write。
- Mem0 OSS v2：当前代码和开发日志为一次提取/更新 LLM 调用/write；CPU embedding 不占该 API 调用费。
- A-Mem：base write 1 次分析，其后每 write 2 次（分析 + evolution）；本范围未达到 100 次 evolution 的 consolidation threshold。
- LightMem：第二轮开发的 base write 用了 1 次，下一次 write 用了 10 次（1 次抽取 + 9 次更新）。低情景按以后每个 round 都是 9 次更新；增长情景按第 r 个 round 为 9r 次更新，另加一次抽取。两种情景均为规划假设，不是统计置信区间或严格上界；旧条目反复更新可能继续增加调用。
- 20% 预留只加在未来估计调用上，不给已花金额再加预留。尚未拆分未返回 usage 或平台重试的具体收费。

HTML/slide、已完成 outline、离线 scoring 与 CPU embedding 不需要额外 DeepSeek 调用。保持当前每 round 的 memory 更新计划，没有为了降低报价擅自关闭 LightMem 更新或删除 baseline。

在按次计费下，减少 token 不直接降低接口费；降低付费调用次数才降低这部分成本。Token 仍是上下文占用和计算负担指标，需与按次费用分别报告。
